## Remaining boundaries and release actions

- **Human action:** real group rehearsal, feedback responses, agreed contributions and release sign-off remain pending. [Release checklist](RELEASE_CHECKLIST.md) supplies a seven-minute run sheet and a 15-requirement matrix without inventing agreement.
- **Cancellation deployment boundary:** explicit build/negotiation cancellation is implemented for the current single-process server. It waits for the active solver/provider call to finish, then rolls back before commit. Commit and cancellation use one gate; a completed commit is reported honestly. Closing a tab alone is not cancellation. Multiple backend workers would require a shared job registry; in-memory operation receipts expire after 20 minutes.
- Cooking/waste basket objectives are product-level estimates. Recipe selection uses real recipe durations and stock expiry but is not a joint globally optimal recipe/pack solver. Meal gaps are reported instead of silently buying extra stock.
- Demo catalogue/history are illustrative. A functioning importer or configured model API does not establish current real-store prices, a partner contract, medical-grade validation or a hosted production deployment.
- New ingredient seed entries apply to fresh demo databases. Existing databases were deliberately not reset; deployers must arrange a reviewed data update if they require the new parmesan graph in an existing database.
- Docker runtime was tested on ARM64 only. GitHub remote CI/publication is a separate check after push; no main release or team sign-off is implied by local results.
